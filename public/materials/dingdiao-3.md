# TME 高校 AI Hackathon｜9 个 idea 的 PRD 细化与选题评估

Sep 19, 2026 · @zynestro

## 先把评分规则翻译成选题约束

官方写的是用户价值、可行性、创新性三条。真正决定名次的是它们背后的四条隐含约束。

**一、有一条没写出来的第四标准：TME 能不能直接吃掉。** 大赛亮点写明“优秀作品将落地腾讯音乐旗下产品中的真实业务场景”，获奖即让渡全部著作财产权。评委是 TME 技术委员会，他们的打分函数里“这东西我下个版本能不能排”权重极高。需要新硬件、需要 BD 谈合作、需要动版权结算链路的方案，天然扣分。

**二、决赛要求“成功部署上线”，这是最狠的一条。** 初赛（10 月 9 日）只要方案简介加 Demo；决赛（11 月 2 日）要“完整产品方案（成功部署上线）”。选题必须是两个人能真部署出来、评委用手机点开就能玩的东西。

**三、由此推出对赛道一的关键判断。** 你担心的“赛道一只能画原型图”不是小问题，是结构性劣势。静态 Figma 对上别人能跑的 Demo，在可行性和 Demo 完成度这项上直接掉档。

所以：**选赛道一的前提是，核心技术点能脱离 App 外壳、单独做成一个可跑的网页 Demo。** 也就是这个功能的灵魂得是一段算法或音频处理，而不是信息架构和界面组织。按这条筛，后面 6 个赛道一点子里，G（歌单标签）会被直接淘汰，F（运动手势）也基本出局。

**四、你们的不对称优势在音乐专业认知，不在工程量。** 20 天、2 人、各自还有科研和实习。拼工程规模必输。但你是真在玩乐队、做 PGM、用 MainStage 和 Studio One、跑过 RVC 的人。评委里一定有音乐人，他们一眼能看出哪个方案是懂音乐的人做的。**该选那种外行做不出来、内行一看就服的题。**

**五、两个务实提醒。**

- 版权：获奖后财产权永久归 TME，衍生产品也归 TME。别把你真想长期自己做的东西拿来投。
- 素材：规则要求如实披露第三方开源与素材。Demo 别用商业歌曲原始音轨，用自己唱自己弹的，或明确 CC 授权的。

下面 9 个方案按同一套简化 PRD 结构写：问题洞察 → 目标用户 → 核心场景 → 功能清单（标出 MVP 线）→ 技术路径 → Demo 边界 → 为什么现在没人做 / 风险。

## A. 赛道二 · Rehearsal Lab：合练的课前预习与课后复盘

你的直觉对一半。**实时合奏这条路要彻底放弃**，但不是因为市场小，是因为物理。北京到上海光 RTT 就 30ms，再叠声卡缓冲，进不了 25ms 的合奏阈值。[JackTrip](https://github.com/jacktrip/jacktrip)、[Jamulus](https://en.wikipedia.org/wiki/Jamulus)、SonoBus、JamKazam 已经把这条路走到头。在这条路上做任何东西都只是 JackTrip 的劣化版，评委一句“你跟 JackTrip 比呢”就问倒了。

**一句话定义**：不用凑齐人，也能把下次合练提前排完。

**问题洞察**：校园乐队缺的不是网络，是四个人同时空着的那两小时。而这两小时里前 40 分钟通常浪费在本可以单独完成的事上：对 BPM、划段落、确认间奏几小节，以及那场永远吵不完的“到底是鼓拖了还是贝斯抢了”。痛点切片是：**合练时间被用来做非合练的事，而争议无法被证据终结。**

**目标用户**：高校乐队 5–10 万支、活跃乐手 30–100 万，加校外业余乐队约百万级。诚实说：**这个盘对 TME 不够大**，它不会为此建独立 App。落地形态只能是 TME Studio 里的一个能力模块。路演里自己先讲出来，比被评委问出来强。

**核心场景**：主唱丢一首要排的歌 → 系统 30 秒内吐出 Click 轨、段落地图（intro/verse/chorus 小节号）、四份抽掉你自己声部的练习音轨 → 各人在宿舍跟同一条 Click 录自己那轨 → 周五排练前群里弹出虚拟合练版和一份报告：副歌第 37–40 小节，鼓平均超前 28ms。到了排练室直接从第 37 小节开始。爽点是那一刻——**争论变成了一张图。**

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 原曲 → Click + 段落地图 | 节拍/downbeat/结构自动分析 | 是 |
| 分轨 minus-one | 去掉指定声部的练习垫 | 是 |
| 浏览器录制 + 延迟校准 | chirp 拍手对齐，补偿设备延迟 | 是 |
| 自动合成虚拟合练版 | 同源 Click 天然对齐 + 互相关微调 | 是 |
| 逐小节 timing 报告 | 每声部相对 grid 的偏差热力图 | 是 |
| 声部间咬合度 | kick↔bass、鼓↔扫弦互相关 | 是 |
| 版本对比 / AI 补位鼓 | 哪些小节变准了；缺鼓手时生成鼓轨 | 决赛 |
| 排练室/琴房排期 | 明确不做，是运营不是技术 | 否 |

**技术路径**：分离用 Demucs v4（htdemucs\_ft）本地 4090 跑；节拍与结构用 madmom 的 DBNDownBeatTracker；因为 Click 同源，**不需要盲对齐**，只需补偿设备往返延迟——播放已知 chirp 让用户拍手校准，服务端用 GCC-PHAT 对齐到 ±1ms（你那套时序/网络本事的降维使用）。onset 用 librosa superflux，音高用 RMVPE。后端 FastAPI + Celery，GPU worker 走 frp 内网穿透挂自己的 4090。

**Demo 边界**：10.9 前单曲闭环，两人各录一轨合成虚拟合练版加一页报告；视频高潮就是“我们本来以为是鼓的问题，报告说是贝斯”。11.2 前部署上线的 Web 站，乐队空间、多人异步上传、版本对比。

**为什么现在没人做**：异步协作这条路有尸体（Bandhub 2019 关停），[BandLab](https://www.bandlab.com/) 和 Soundtrap 是云 DAW，能协作但不做排练分析。[Moises](https://moises.ai/products/moises-app/) 做分轨变速，是**单人练习**视角；[MatchMySound](https://matchmysound.com/) 做乐谱跟随打分，是**单人对谱**。真空地带很清楚：**没人做多声部合奏的 timing 一致性分析**。原因不是技术难，是市场太碎，大厂看不上，独立开发者又缺乐队真实体感。

**致命风险**（1）用户规模天花板；（2）手机录 + 耳机漏音会把 timing 数据毁掉，报告就是假的；（3）**音乐学效度陷阱**——人类 groove 本来就不在 grid 上，鼓手 laid-back 是风格不是错误。必须提供“对齐到参考演奏”而不只是“对齐到绝对 grid”，这是专业与否的分水岭。

**评分**：用户价值 8 ｜ 可行性 8 ｜ 创新性 7 ｜ TME 可落地 5

## B. 赛道二 · 琴谱重听：把六百年没人弹的减字谱读出声

先枪毙原始想法：**照着古筝 App 做一个古琴触屏模拟，不但不够创新，而且在乐器学上就不成立**。古筝的音乐性在右手拨弦、音高被雁柱钉死，触屏能还原七八分；古琴的音乐性有八成在左手的走手音（吟、猗、绰、注都是连续滑音和余韵），触屏做出来是个残废玩具，古琴圈第一眼就会否掉。

**一句话定义**：拍一页古琴谱，听见它本来的样子。

**问题洞察**：**减字谱不记节奏**。它只记“哪根弦、第几徽、什么指法”，唯独不记时值。初学者拿到《神奇秘谱》影印页，根本不知道该弹出什么声音。关键洞察是：**这里面有一半是完全确定的**——弦序加徽位配上定弦，音高是纯物理可算的；只有节奏不确定，那部分才叫打谱。AI 该做的是把确定的那一半自动化，把不确定的那一半变成人机协作。

**目标用户**：国内古琴学习者数十万到百万量级。**靠人群数量拿不到分，所以定位必须换**：不说“给古琴学习者的练习 App”，要说“**古琴谱数字化引擎**”：存世古琴谱集百余部、曲目三千余首，其中绝大多数从未被今人弹响过。不是“帮 50 万人练琴”，是“让六百年没人听过的曲子发出声音”。评委会记住后面这句。

**核心场景**：琴友拍一张《秋风词》老谱影印件传进网页 → 三秒后出现虚拟琴面，减字被逐个框出并译成「七弦 · 九徽 · 挑」→ 点播放，徽位依次亮起，声音出来了，带着绰注的滑音 → 发现第三行有个字识别错了，点一下改正，音频实时重算。爽点是“原来它是这么响的”那一秒。

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 减字谱图像 → 单字切分 | 竖排版面分析 + 检测 | 是 |
| 减字部件识别 | 指法/弦序/徽位三头分类 | 是 |
| 规则化音高映射 | 徽位→弦长比→频率，零幻觉 | 是 |
| 虚拟琴面可视化 | 徽位高亮 + 指法动画 | 是 |
| 采样合成 + 走手音 | 吟猗绰注的 pitch envelope | 是 |
| 人工纠错界面 | 识别错了一点就改 | 是 |
| 节奏候选（打谱助手） | 等时/句读/对齐名家录音 | 决赛 |
| 导出 MIDI / MusicXML | 给老师和 DAW | 决赛 |

**技术路径**：减字是**合成字**，整字分类会撞上长尾，必须走部件分解路线——YOLO/DETR 检出单字框，再多头分类出指法部件 + 弦序 + 徽位。开源底子：[guqinMM](https://github.com/wds-seu/guqinMM)（东南大学，MIT，已开减字数据集与分解树）、[ACL 2026 零样本减字识别](https://aclanthology.org/2026.acl-long.1356.pdf)、[Springer 的 YOLO 部件识别](https://link.springer.com/chapter/10.1007/978-981-95-3141-7_11)。用减字谱输入法的字形批量渲染合成训练集做增广，4090 上几小时就够。

**音高映射不用 AI**——徽位是弦长的整数分点，按音 f = f₀·L/(L−x)，这段是确定性代码。路演时要专门强调**可解释、零幻觉**，这在一个满场 AI 生成的比赛里是稀缺的可信度。吟猗是 4–7Hz、±20–50 cents 的 LFO 调制，绰注是起音前的 portamento——这块正好是你玩 Vocaloid 6 的手感区。决赛的节奏候选有一招很漂亮：用 CREPE 提名家录音的 f0 序列，与规则生成的音高序列做 DTW 对齐，**反推出节奏**。

**为什么现在没人做**：**有人做了一半**。[丝桐里](https://apps.apple.com/cn/app/%E4%B8%9D%E6%A1%90%E9%87%8C/id1528654915)（iOS，4.8 分，季订 ¥88）已有减字谱输入法、同步播放陪练、调音器、音位图、曲库，做得很扎实。但它们全是**手工录入**——你得先自己一个字一个字敲进去。**没人把 OCR 这一步接上。** 学术侧反而跑在产品前面：guqinMM 开了数据但没开预训练模型，生成部分还写着 to be continued。真实情况不是“没人想到”，是**技术刚刚成熟、还没人产品化**——hackathon 的甜点区。

至于“小众但深”在这个比赛是加分还是减分：**对用户价值和可落地性是减分，对创新性是大加分**。TME 有国风内容标签和长音频业务，包装成“AI + 非遗”的 PR 案例比落地成工具容易得多。

**致命风险**（1）古籍影印本上准确率可能崩（木刻本墨色不匀、异体字、竖排粘连），必须提前拿《神奇秘谱》影印页测一版并诚实报数；（2）合成音色的说服力——古琴圈耳朵极毒；（3）规模天花板。

**评分**：用户价值 6 ｜ 可行性 7 ｜ 创新性 9 ｜ TME 可落地 5

## C. 赛道二 · 合唱团：你唱一句，他们四个在唱

先把话说死：「唱一句自动出和声」**已经有成熟产品**。[Voloco](https://voloco.com/)（千万级下载）实时 autotune + harmony + 八轨录音，全民K歌有一键修音和和声，抖音有一堆变声特效。如果方案是“我们也做自动和声”，评委三十秒内搜到 Voloco，这个 idea 就死了。

但里面有个真缝。**所有现有玩法给你的都是“更多个你”**：Voloco 是同一条人声的 pitch-shift 复制，听起来仍是你，只是变厚；Antares Harmony Engine 这类专业插件给的是音乐上正确但**没有人格**的声部。**没人做“更多个人”**——低音是个厚嗓大叔，高音是个亮的女声，中间垫一个气声的，每个人有名字有头像。合唱的魅力从来不在音程，在**不同的人一起唱**。用户要的不是厚，是热闹。

**一句话定义**：录一句，给你一整个有人设的合唱团。

**目标用户**：泛 K 歌/短视频用户，国内 K 歌月活亿级。这是赛道二三个 idea 里**唯一量级够大、TME 会真的在意**的一个。

**核心场景**：刷到一条“你只唱了一句，但他们四个都在唱”的视频 → 点进落地页唱八秒副歌 → 五秒后蹦出四张角色卡：老周（低音，厚）、小满（高音，亮）、阿雾（气声垫）、还有你自己 → 点播放，四个明显不同的嗓子在唱你刚才那句 → 嫌阿雾太飘，一键换人 → 导出纵向四格视频，谁唱谁那格亮起来。爽点在第一次播放的那两秒：**这不是我的四个复制人，是四个人。**

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 录一句（≤15s） | 移动端浏览器录音 | 是 |
| 调性/和弦判定 | 决定和声音程的前提 | 是 |
| 调内和声声部生成 | 三度/六度/八度，非固定半音 | 是 |
| 音色角色卡（5–8 个） | zero-shot 歌声转换 | 是 |
| 合唱团化处理 | 随机微延迟/微失谐/声像 | 是 |
| 多格视频导出 | ffmpeg，谁唱谁亮 | 是 |
| 换人/solo/踢人 | 交互爽点 | 是 |
| 自制角色卡 / 好友合唱团 | 传 10s 自己的声音；社交裂变 | 决赛 |
| 实时处理 | 明确不做 | 否 |

**技术路径**，逐个回答你的疑问。

**和声怎么才不难听**：第一步必须定调，固定 +4 半音平行移调一定难听。干唱时从 f0 序列（RMVPE）统计音级直方图，用 Krumhansl-Schmuckler 算调性，几十行代码；有伴奏时直接上 [madmom](https://github.com/CPJKU/madmom) 的和弦识别。**大三度还是小三度——不选，由调决定**：走调内三度，C 大调里 C 上方是 E（大三）、D 上方是 F（小三），自动就对了。进阶是逐音吸附到当前和弦的和弦音。

**音色多样性从哪来**：不能用 formant shift，那个出来是花栗鼠和大叔，塑料感正是 Voloco 的天花板。用 **zero-shot 歌声转换**——[seed-vc](https://github.com/Plachtaa/seed-vc)（GPL-3.0，44.1kHz，200M，明确支持 zero-shot singing voice conversion）。零样本意味着不用为每个音色训模型，一段十秒参考就是一张角色卡。这也正是“为什么是现在”的答案：2023 年做这个要给每个音色训一个 RVC 模型，成本结构根本不成立。

**让它像合唱团而不像复制人**：移调用 formant-preserving（Rubber Band 的 formant 模式，注意 GPL/商用双许可；或用 BSD 的 WORLD），每个声部加 ±8–15ms 随机延迟、±5 cents 随机失谐。完全 unison 会产生梳状滤波，听起来像相位问题而不是合唱。

**关键取舍：不做实时**。seed-vc 算法延迟约 300ms 且吃 GPU。就做“录完五秒出结果”，这条要在 PPT 里主动讲，是可行性的加分项不是减分项。

**为什么现在没人做**：三层。一，“自动和声没人做”是假的，别当创新点。二，“多音色人格化合唱”确实没人做，因为 2024 年之前 zero-shot 歌声转换质量不够；且**大厂有合规顾虑**——深度合成规定要求标识与授权，民法典对声音参照肖像权保护，全民K歌那个体量不敢轻易开放任意音色；三，这是玩法不是留存，ROI 算不过来。三条加起来是一条**小团队做得了、大厂不方便做**的缝——但同一个原因也意味着 TME 落地时法务会先砍一刀。主动交代：只用自录或已授权音色库、绝不碰明星音色、所有输出打 AI 标识。

视觉形式上要点名 [Acapella from PicPlayPost](https://apps.apple.com/us/app/acapella-from-picplaypost/id924635678)：多格合唱视频的传播力它已验证过，但那需要你录四遍，这里只录一遍——这就是差异话术。

**致命风险**（1）Voloco 正面撞车，音色差异必须一耳朵听得出；（2）声音克隆合规；（3）四个声部各跑一次转换，4090 单机在路演现场会排队到崩，必须预生成兜底。

**评分**：用户价值 7 ｜ 可行性 8 ｜ 创新性 7 ｜ TME 可落地 8

## D. 赛道一 · 全民K歌：音域指纹与“这首歌该升降几个调”

**一句话定义**：30 秒测出你的舒适音域，给每首歌算出专属升降调数。

**问题洞察**：K 歌用户失败的第一现场不是跑调，是**选错了调**。副歌一到最高音就破音、卡嗓、破罐破摔。全民K歌早就有升降调按钮，但它把决策全推给用户：一个不懂乐理的人只能点“-1、试唱、还是高、-1、再试”，试三次就放弃。**升降调功能的存在本身证明了需求，而它的易用性证明了问题没被解决。**

**目标用户**：“会用升降调但不会用对”的中间层。TME 2025 Q3 在线音乐移动 MAU 5.51 亿且同比下滑 4.3%（[21财经](https://www.21jingji.com/article/20251114/herald/5c615384d3754610201b25ee4eb01a4e.html)）。在 MAU 下滑的背景下，任何提升“单次录唱成功率”的功能都在 OKR 正中央。

**核心场景**：新用户→ 弹出“唱一句测音域”→ 30 秒得到一张音域卡片（如 F2–A4，舒适区 A2–E4，“男中偏低”）→ 回到曲库，每首歌封面角标不再是难度星级而是 **“-3”、“0”、“+2”** 的变调数字 → 点《晴天》显示“建议 -2，原调最高音 F#4 超出你舒适区 4 个半音”→ 一键应用，副歌没破音。

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 30 秒音域测试 | 跟唱设计好的滑音+歌词片段 | 是 |
| 音域卡片与分享 | 钢琴键可视化 + 声部标签 | 是 |
| 歌曲音域索引 | 离线跑曲库，存最低/最高/tessitura | 是（Demo 100 首） |
| 变调推荐数 | 核心：算出 -N/+N 半音，一键应用 | 是 |
| 按音域筛歌单 | “适合你唱的 50 首” | 是 |
| 音区/共鸣腔识别、换声点标定 | 见下方诚实结论 | 否 |

**技术路径**

1. **测试设计：不要唱音阶。** 让普通人跟钢琴唱 do-re-mi 是尴尬感和失败率的主要来源。三段式：（a）跟唱一句熟悉歌词做基准定位与暖嗓；（b）**向下滑音**到唱不动；（c）**向上滑音**到破音。滑音是连续信号，对基频跟踪极友好，且不要求用户认识音名。
2. **基频提取**：浏览器端首选 [SPICE (TF.js)](https://www.gstatic.com/aihub/tfhub/demos/spice.html)，零后端；更高精度用 [SwiftF0](https://arxiv.org/html/2508.18440v1) 的 ONNX 跑 onnxruntime-web（95,842 参数，CPU 快约 42×，10 dB 信噪比下谐和均值 91.80% vs CREPE 78.97%）。手机录音噪声大，**抗噪比绝对精度更值钱**。
3. **舒适 vs 极限判定**：不靠音高本身，靠**稳定性代理指标**——jitter、RMS 能量跌落、HNR 下降。三项同时恶化的点 = 极限下沿；能稳定保持 1.5 秒以上的区间 = 舒适音域。这是工程近似，PRD 里要写明。
4. **歌曲侧索引**：htdemucs 分离人声 → torchcrepe 提 f0 → 中值滤波去八度错 → 统计最高/最低音与 **tessitura（10%/90% 分位，即常驻音区）**。4090 上 100 首约 1–2 小时。不需要全曲库——这是离线批处理，TME 侧上线时是纯算力问题。
5. **变调算法**（核心）：不是“让最高音落进你音域”，而是最小化加权代价

```latex
\mathrm{cost}(k) = w_1\max(0,\, P_{90}+k-U_{hi}) + w_2\max(0,\, U_{lo}-P_{10}-k) + w_3|k|
```

w₃ 惩罚大幅变调（伴奏移调过多会音色失真），取 argmin 即推荐值。**这比推荐歌单强得多**：歌单是“你不能唱这些”（负面、限制感、剥夺用户选择自由），变调数是“你想唱的这首，这样唱就行”。前者是过滤器，后者是修复器。

**音区/共鸣腔能不能做——能分类，但不该进 MVP。** 最新工作用 mel 纹理特征做胸声/头声二分类，SVM 94%、CNN 96.2%（[arXiv 2505.11378](https://arxiv.org/abs/2505.11378)），但该数据集只有 1008 个片段、**仅限当代男声流行、音高集中在 A3–G4**，作者自己写明无法推广。**换声点更糟**：即使用 EGG 直接测声带接触，18 个未受训男性中**只有 10 人**出现可检测的振动不规则（[JVoice](https://www.sciencedirect.com/science/article/abs/pii/S0892199709000708)）。至于 singer's formant，它是**美声训练歌手**的标志，在素人身上几乎不成立。结论：做成 V2 的趣味标签可以，做成 MVP 的判定依据会砦掉可信度。

**能不能做成可跑 Web Demo**：能，且**零后端**。getUserMedia → AudioWorklet → SPICE/SwiftF0 实时出 f0 → Canvas 画实时音高曲线（滑音时用户能看见自己的线往下掉，这个视觉反馈本身就是爽点）→ 查一份预先算好的 100 首歌 JSON 索引（几百 KB）→ 算变调数 → SoundTouch.js 实时移调试听。纯静态站点，扯 Vercel 就跑。

**为什么全民K歌现在没做——它做了，只是没给用户看。** TME **天琴实验室**在公开技术分享中明确写道，其歌唱评价体系的用户维度包含“**音域维度包括音域上界和下界，舒适音域和极限音域**”，并设有“发声共鸣相关分支”（[天琴实验室](https://community.aijishu.com/a/1060000000403471)）。算法能力早就在，但被埋在**打分系统**里当评测特征，从未变成一个用户能主动调用、直接驱动选歌与变调决策的入口。

**已有对标**：Smule 的 **Simply Sing** 已做了“测音域 → 歌曲自动移调到你的音域”（[评测](https://sing.salon/articles/tech-reviews/simply-sing-review-practice-singing-in-your-vocal-range-r41/)）；独立 App **Vocal Gauge: Range Transposer** 做了测音域 + 一键 Put In Range（[App Store](https://apps.apple.com/us/app/-/id1624908530)）。**这意味着“音域+变调”组合不是新概念，创新分必然受损。** 差异只能来自三点：滑音式 30 秒流程、tessitura 分位而非仅极值、华语曲库（Smule/Vocal Gauge 在华语歌上几乎是空的）。

**致命风险**（1）**已有同类直接压创新分**，且天琴实验室自己就有音域算法——坐着 TME 的人第一句就是“我们内部有”；（2）伴奏移调 ±3 半音以内尚可，超过就明显失真，而低音男声唱女歌需要 -5 以上；（3）同一个人早晚音域上限能差 2–3 个半音，一次测定长期沿用会产生“不准”口碑。

**评分**：用户价值 8 ｜ 可行性 9 ｜ 创新性 5 ｜ TME 可落地 9

## E. 赛道一 · 全民K歌：自听还原，让回放听起来像你自己听自己

**一句话定义**：一个开关，把录音还原成你脑子里自己的声音。

**问题洞察**：K 歌用户流失的隐形漏斗是**录完不发**。用户唱得其实还行，但一点回放，听到一个陌生、扁平、发尖的声音，瞬间自我否定。这在心理学上叫 voice confrontation。**问题不在用户唱得差，在于播放链路从物理上就不是他听惯的那条路。** 而全民K歌把大量资源投在“让你唱得更好听”（AI 修音、DTS 音效、臻品母带），没人投在“让你认得出这是自己”。前者修的是音准，后者修的是身份认同。

**核心场景**：录完点回放，皆眉。播放器上出现一个新开关\*\*「自听模式」\*\*。点开，进入 40 秒引导：屏幕上只放你刚录的同一句的两个版本 A 和 B，问“哪个更像你平时听到的自己”——连问 6 轮。第 7 轮结束，切到自听模式，用户听到那个熟悉的、低沉一点、不那么刺耳的自己，“哦，这才对”。**爽点不是变好听，是变成我。**

### 技术澄清：“只加低频行不行”

**结论：不行。只 boost 低频最多做到 30% 的效果，剩下 70% 在中高频的衰减上。**

**（a）低频确实要加，但范围比你想的宽。** 有文献直接测过这条传递函数：Won 等人用歌唱信号估计的“气导→骨导”传递函数呈现 **3000 Hz 以下抬升、3000 Hz 以上衰减**，峰值可达 +19 dB、谷值 −23 dB（[ICMC 2005, Stanford CCRMA](https://ccrma.stanford.edu/~sywon/research/OnesOwnHearing/SingingTF/ICMC2005.pdf)）。**但这是单个女高音的数据**，只能采纳它的形状，不能拄幅度。另一项用特制耳罩分离两条路径的研究发现，**骨导分量在 1–2 kHz 区间压过气导**（[Reinfeldt & Stenfelt](https://pubmed.ncbi.nlm.nih.gov/20707445/)）——是 1–2 kHz，不是 200 Hz。“只加 80 Hz 以下的超低”是错的。

**（b）关键的、被所有人忽略的一条：2–4 kHz 必须衰减。** 外耳（耳廓+耳道）构成一个共振腔，在约 **3000 Hz 提供高达 +20 dB 的增益**（[Cochlea.eu](https://www.cochlea.eu/en/ear/external-ear/)）。这个增益对录音回放的相对关系不生效：手机麦是在嘴正前方近距离轴上拾音，捕获的是高频最完整的那一路；而你听自己时声音要绕过头部（头部阴影，高频衰减最剧烈）才到耳朵。结果就是**录音里 2–4 kHz 的刺锉感系统性地高于你的自听体验**。这才是“听起来像陌生人且特别刺耳”的主要来源。**第一刀应该砸在 2–4 kHz，而不是加 100 Hz。**

**（c）4 kHz 以上要砍得更狠。** 同一逻辑在 4–10 kHz 更明显。

**（d）近讲效应是个反向干扰项。** 手机贴近嘴录会触发 proximity effect，本身已经给录音加了低频。再照默认曲线加低频会轰头。必须先做一次低频能量归一化。（工程判断，非文献结论）

**（e）堵耳效应是可利用变量，也是陷阱。** 封堵耳道时自己说话的低频声压在耳道内被放大：**500 Hz 以下 20 dB 或更多**（[Hearing Research](https://www.hearingresearch.org/drross/occlusion.htm)），250 Hz 处实测约 **25 dB**（[Hearing Review](https://hearingreview.com/hearing-products/accessories/earmolds/solving-the-occlusion-effect)）。但注意：堵耳效应作用在**用户实时发声**时，而回放时用户不发声——所以它不能算进回放链路，反而意味着**戴不同耳机的用户对同一条曲线的主观感受会不同**——这正是必须做个性化、而不是出厂一条曲线的硬理由。

**（f）混响与麦克风染色**：严格做要去混响，但 MVP 建议不做（会引入 artifact，且全民K歌回放链路本来就叠了自家混响）。

**可直接写进 PRD 的目标 EQ 曲线草案**（作用于干声，增益归一化后）：

| 频段 | 方向与幅度 | 依据强度 |
| --- | --- | --- |
| 60–150 Hz | Low shelf **+2 \~ +6 dB** | 方向有文献；幅度为工程近似，需按近讲效应回退 |
| 150–800 Hz | Peaking **+2 \~ +5 dB**, Q≈0.7 | 有文献（骨导主导区） |
| 1–2 kHz | **0 \~ +2 dB** | 有文献（Reinfeldt & Stenfelt） |
| **2.5–4 kHz** | Peaking **−3 \~ −7 dB**, Q≈1.0 | **核心的一刀**。方向有文献；幅度为工程近似 |
| 5–10 kHz | High shelf **−4 \~ −9 dB** | 方向有文献；幅度为工程近似 |
| 整体 | LUFS 响度归一化 | 工程必需，否则 A/B 时用户会把“更响”误判成“更像” |

哪些是文献、哪些是猜，**要在路演 PPT 上明写**。这条诚实度本身会加分。

### 个性化交互：推荐 A/B 逐步逼近，而且有文献背书

你提的三个选项里，**“让用户自己选 EQ 预设”是最差的**（普通用户听不出区别，且预设是离散的）。**二维触摸球是对的直觉，但是错的交互形态。**

关键证据：Won & Slaney 做过一个双参数自听模拟模型 `M = Filter1 + α·Filter2 + β·Filter3`，Filter2 管 **864 Hz 以下**、Filter3 管 **864 Hz 以上**。被试用两个滑块调到“像自己”，**接近度评分达 80–95**，且**未发现性别或歌唱经验会系统性区分传递函数**（[Won & Slaney, ICMPC 2014](<http://www.slaney.org/malcolm/Microsoft/Won2014(BoneConductionSimulationForICMPC).pdf>)）。

这给了两个直接结论：**两个参数就够了**，你的直觉是对的；**但滑块要求用户理解自己在调什么**，在 C 端是灾难。

**推荐：把这两个参数藏在 6 轮强制二选一的 A/B 背后。** 系统对 α 和 β 交替做二分搜索（各三轮），6 轮 ≈ 40 秒，用户零认知负担。**触摸球要求用户主动探索一个他不理解的二维空间，A/B 只要求他做他天生就会的事——比较。**

**关于“录一段说话做少样本个性化”**：诚实评估——**这条路在物理上不成立**。要反推骨导传递函数，需要该用户的**自听参考信号**，而自听信号本质上无法被外部麦克风采集——这正是整个问题的起点。没有 ground truth 就没有监督信号。**唯一可用的自动化信息是从录音里估计近讲效应强度和混响量，用来设 A/B 的起点，把 6 轮压到 4 轮。**

**实验设计陷阱**：A/B 素材**必须是用户自己刚录的那段**。用别人的声音做校准，测出来的是审美偏好不是自听还原。

**能不能全在浏览器里做完：能，而且是本方案最强的一点——100% 前端，零后端、零模型。** 4–5 个 `BiquadFilterNode` 串联就是上表那条曲线；**同一个 `AudioBufferSourceNode` 喂两条并行滤波链**，各接一个 GainNode，`setTargetAtTime` 做 10ms 交叉淡入——保证 A/B 播放位置完全对齐，错开 50ms 就毁了。响度用 `OfflineAudioContext` 预渲染算 LUFS 差补平。`localStorage` 存 (α, β) 两个浮点数。**实时监听（耳返）MVP 不做**：浏览器实时延迟 20–200ms 不可控，而回放态处理没有任何延迟问题，效果完全一样。

**为什么全民K歌现在没做**：不是技术问题，是产品方向盲区。它的全部音频投入都在“美化”轴上。两个目标在频响上甚至是**冲突的**：修音/母带通常会**抬高** 2–5 kHz 让声音更亮，而自听还原要**压低**这一段。一个团队很难同时相信这两件事。

**已有产品点名**：助听器行业做得最深——Signia 的 **Own Voice Processing 2.0** 为佩戴者自己的声音开一条独立通道，训练不到 10 秒（[Signia Pro](https://www.signia-pro.com/en/blog/global/2022-05-backgrounder-signia-ax-own-voice-processing-20/)）。**但它的目标是相反的**——助听器要解决佩戴者觉得自己声音太响太闷（堵耳效应），所以它在**衰减**低频；我们要**增强**低频、衰减中高频。同一套物理，相反的产品目标——这个对照在路演上说服力极强。**K 歌/录音类 App 中没有找到对标。没有任何主流产品把“还原自听”作为一个显式产品概念。**

**致命风险**

1. **效果的主观性无法证伪，Demo 可能讲不出来。** 评委听你的自听版，他听到的只是“低频多了点高频少了点”——因为**那不是他的声音**。现场必须设计成“请一位评委上来录 10 秒”。**这是结构性风险。**
2. **“更像我”不等于“更愿意发布”。** 如果 11.2 的主观实验做出来发现发布意愿没有显著提升，整个用户价值论证就塌了。必须提前做。
3. **与现有音效链路冲突**：必须插在干声之后、音效之前，这需要改 TME 的音频图，落地成本比看起来高。

**评分**：用户价值 7 ｜ 可行性 10 ｜ 创新性 9 ｜ TME 可落地 6

## F. 赛道一 · QQ音乐：运动场景无屏操控（不建议做）

你的“不知道有没有必要”是对的。**结论：不建议做。**

**逻辑死结**：要摇手机，手机必须在手上；手机在手上，直接点屏幕比摇晤更快更准。而手机在臂带、腰包或跑步机置物槽时，摇晤手势根本无法执行。**你描述的痛点场景，恰恰是这个方案物理上覆盖不到的场景。**

**上游已被吃干净**：耳机侧的双击、三击、长按（[华为 FreeBuds 手势](https://consumer.huawei.com/cn/support/content/zh-cn15965352/)、AirPods 捏杆、小米与 OPPO 同类方案）全部原生支持上下一首和暂停，而且手就在耳边。**播放控制是终端厂商的地盘，不是内容 App 的地盘。**

**误触代价不对称**：跑步步频 150–180 spm（2.5–3 Hz），垂直冲击峰值 2–4g，与“剧烈摇晤”在加速度幅值上同量级。漏检的代价是“还得掉手机”（等于没做），误触的代价是“跑到一半歌突然停”（比不做更糟）。可用门槛大约是漏检率低于 2% 且每小时误触不超过 0.5 次，20 天内既做不到也验证不了。

**Demo 层面直接判死刑**：Web 端只能用 DeviceMotionEvent，iOS Safari 需用户手势授权、后台不给传感器数据。**真实场景下手机是锁屏的，Web Demo 永远演示不了真实使用条件。**

**重构方向也已被证伪**：[Spotify Running 于 2018-02-26 正式下线](https://community.spotify.com/t5/Content-Questions/Retirement-of-our-Running-Feature/td-p/4383603)，它做的正是“检测步频 → 匹配同 BPM 歌曲”。下线原因是根本性的：要正好 172 BPM 且用户爱听的歌，曲库交集极小，只能变速播放，一变速音色就垮。Nike Run Club、Adidas Running 也都试过同一条路。心率-歌单路线则拿不到数据——心率在手表厂商手里。

把 20 天投进去，最好的结果是做出一个精致的、评委一眼看穿“我耳机上捏一下就行”的 demo。

**评分**：用户价值 3 ｜ 可行性 4 ｜ 创新性 2 ｜ TME 可落地 2

## G. 赛道一 · QQ音乐：排练模式（从歌单到 Setlist）

你自己的直觉对：原始想法（多加标签）确实没救。三个重构方向里：

- **LLM 自动生成个人事件标签**：否决。需要用户长期真实听歌行为流，你拿不到，Demo 只能编数据。而且 [QQ音乐 2025 年已上线“AI 智能歌单”](https://sj.qq.com/blog/1743588996000)（自然语言描述生成歌单），正面撞车。
- **演唱会预习歌单**：降为附属。[setlist.fm 有公开 API](https://api.setlist.fm/docs/1.0/resource__1.0_artist__mbid__setlists.html)，但数据以欧美 live 为主，华语歌手巡演覆盖稀薄——是个“接口通了但数据是空的”陷阱。
- **乐队排练歌单**：**选这个。** 因为你本人就是键盘手，是你唯一有一手洞察、能自己当被试、能一眼判断输出对不对的方向；而且 key/BPM/和弦/段落全是客观可计算的 MIR 量，不靠主观标注。

**一句话定义**：把歌单自动变成带调性、速度、和弦、段落的乐队排练单。

**问题洞察**：周六下午三小时排练房，四个人到齐。主唱说“这首我唱不上去”，键盘手要当场算降小三度后的和弦；鼓手问“副歌前那个 break 是几拍”。今天这套活是：QQ音乐听歌 → 切到 Tunebat 查 key/BPM → 切到虫虫吉他找谱 → 在微信群里发文字。**QQ音乐拥有全量音频，却只提供“播放”这一个动词。**

**目标用户**：国内活跃乐队与翻唱团体数十万支，加独立音乐人、KTV 重度练歌用户，可触达百万级。窄，但极高频、极高付费意愿。

**核心场景**：键盘手建一个“11月校园音乐节”歌单，丢进 12 首歌，点“排练模式”。30 秒后每首歌左侧多了一行：`C#m · 138 BPM · 4/4 · 前奏8小节`。点进去看到段落时间轴和每段和弦进行，点“副歌”直接循环那 24 秒。主唱说高了，拖移调滑块到 -2，和弦表整体变成 Bm，音频变调不变速同步跟上。排完点“生成 Setlist”，按调性相邻度和 BPM 能量曲线给出建议顺序，导出一张图发进乐队群。

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 歌单批量分析 | 每首出 key / BPM / 拍号 | 是 |
| 段落结构时间轴 | intro-verse-chorus-bridge-outro | 是 |
| 和弦进行提取 | 按段落输出和弦序列 | 是 |
| 段落循环练习 | 点段落即 loop，变速不变调 | 是 |
| 移调助手 | 滑块移调，和弦表+音频同步 | 是 |
| Setlist 编排器 | 按调性/BPM/能量曲线排序 | 11.2 |
| 排练单导出 | 图片/PDF，分享给成员 | 11.2 |
| 分轨静音 | Demucs 抽掉某个乐器轨 | P1 |

**技术路径**：全部跑在浏览器。[essentia.js（WASM 版 Essentia）](https://mtg.github.io/essentia.js/) 提供 `KeyExtractor`、`RhythmExtractor2013`、`HPCP` + `ChordsDetection`。段落结构用 MFCC/CQT 算自相似矩阵 + Foote checkerboard kernel 做 novelty 峰值检测（或直接接 allin1/msaf）。变速不变调用 SoundTouch.js 或 RubberBand WASM。移调后的和弦表是纯符号变换。

**能不能做成可跑 Demo**：能，而且是赛道一里脱壳最干净的之一。纯前端静态页，零后端。离“可信”的距离也最短——**因为 key 和 BPM 有客观答案**：选 20 首自己弹过的歌人工标注 ground truth，在 Demo 里直接放准确率对照表（预期 key 70–85%、BPM 85–95%）。**敢报准确率，就赢了 90% 的 hackathon demo。**

**为什么 QQ音乐现在没做**：不是做不到，是象限不对。QQ音乐的 KPI 是 DAU、时长、会员转化，用户模型是“消费者”；排练模式服务的是“创作者/表演者”，不涨这三个数。TME 把这块能力放在腾讯音乐人平台那条线上了。**这不是补齐功能，是给 QQ音乐加一个它从未有过的产品象限**，且边际成本极低（曲库算一遍）。

**致命风险**（1）和弦识别准确率会伤到专业用户的信任——MIREX majmin 任务 SOTA 约 80%，中文流行有大量加九/挂留和弦时更糟；缓解是只展示高置信度片段并标注置信度，定位成“排练草稿”而非“官方谱”；（2）TAM 太小；（3）完整和弦谱可能触及改编权，导出的排练单不含完整曲谱。

**评分**：用户价值 7 ｜ 可行性 9 ｜ 创新性 7 ｜ TME 可落地 6

## H. 赛道一 · QQ音乐：万人合唱

**一句话定义**：几千人各唱一句，自动对齐拼成一首完整的歌。

**问题洞察**：抖音评论区“把大家的歌声剪在一起”之所以动人，是因为归属感——但它今天是**纯手工剪辑**，一个创作者剪 100 条片段要熬几个通宵，因此这个内容形态永远是稀缺事件而不是可复用产品。真正的瓶颈不是创意，是“N 个人在 N 种设备、N 种延迟、N 种音准下唱同一段，怎么自动变成一条听起来像一首歌的音轨”。**这是一个纯工程问题，而它恰好没人做完。**

**核心场景**：首页 banner“《孤勇者》万人合唱，第 47 句还缺人”。点进去，整首歌被切成 64 个乐句，每句显示已有多少人唱过。他挑一句，戴耳机跟导唱录 7 秒。上传后 10 秒内，页面播放的成片里就有他的声音——对齐到了毫秒级、音准被修正、响度与前后句一致。页面高亮“你在 1:12–1:19”。他生成一张卡片发朋友圈：“这首歌的第 47 句是我唱的。”

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 乐句认领与录制 | 按歌词切句，浏览器录音 | 是 |
| 自动时间对齐 | 伴奏互相关 + DTW 细对齐 | 是 |
| 音高/响度归一 | f0 校正 + EBU R128 | 是 |
| 演唱质量评分 | 音准/节奏/音色/音质四维 | 是 |
| 分段择优拼接 | 每句独立选优 + 等功率淡化 | 是 |
| 万人合唱垫音层 | 全员叠加，人越多越好听 | 是 |
| “我在哪一句”分享卡 / 奖池抽取 | 定位高亮；20% 乐句留给随机 | 11.2 |
| 内容安全审核 | ASR + 文本审核 + 声纹保护 | P1（落地必需） |

**技术路径（核心资产在这一节）**

1. **时间对齐**。客户端上报的播放位置不可信——Android AAudio 输出延迟 30–200ms，蓝牙再叠 150–300ms。服务端做二次对齐：外放录音（有伴奏泄漏）用 GCC-PHAT 估时延，精度可到 ±5ms；耳机录音（无泄漏）走歌词强制对齐（MFA 或 WhisperX 词级时间戳）；细对齐对 chroma 或 f0 contour 做 DTW，把 warping path 拟合成“线性 offset + 微量 time-stretch”，用 WSOLA 施加——**避免 DTW 的非线性拉伸把演唱韵律毁掉**。
2. **音高归一**。pYIN/CREPE 提 f0 → 先算整体 cent 偏移（有人整体唱低了半音，整体移回去，而不是逐音符硬掰）→ 再对残差做逐音符修音，用 pyworld 或 RubberBand 的 formant-preserving 保住音色。**修音强度必须是可调连续量**：修狠了全是 T-Pain 机械感，修轻了跑调刺耳，这条带子很窄。
3. **响度与音色归一**。pyloudnorm 按 EBU R128 归到 −14 LUFS；再做 matching EQ，把每个片段的频谱包络往参考人声的长时平均频谱靠。
4. **噪声与拼接**。DeepFilterNet 抑噪，Demucs 抽 vocals 去掉漏进来的伴奏，80Hz 高通去 rumble。切点选在歌词时间轴的乐句边界，30–80ms 等功率交叉淡化。
5. **万人合唱垫音层（设计上的关键一招）**。把**所有没被选中的人**全部对齐后叠加成背景合唱层，每条加 ±8ms 随机抖动和 ±5 cent 微失谐（这正是真实大合唱 chorus 效应的物理成因），各降 20dB 求和。不相关噪声求和的信噪比随 √N 提升——**参与人越多，这层越厚越好听**。更重要的是产品意义：每个人都在成品里，**归属感的分发不再是零和的**。奖池只是锦上添花。
6. **谁被选中**。四维打分：音准（f0 与参考旋律的时长加权 cent 误差）、节奏（onset 偏差标准差）、音色匹配度（ECAPA-TDNN 声纹 embedding 余弦距离）、音质（SNR、削波、伴奏泄漏）。两个必须加的约束：**分段独立选优**，以及**多样性约束**（同一用户最多占 2 个乐句）。否则纯客观分必然选出一堆“最像原唱的人”，成品退化成一个人的独唱。

**能不能做成可跑 Demo：能，但需要后端。** 冷启动靠合成数据解决，**而且这恰好是优势不是妥协**：用 RVC/So-VITS 把你自己的一条干声变换成 30–50 个不同音色的“虚拟参与者”，再人为注入不同手机麦的 IR 染色、随机 0–300ms 延迟、±50 cent 音准偏差、MUSAN/DEMAND 底噪。**因为你知道注入的 ground truth offset，你就能报出“对齐误差中位数 8ms、P95 22ms”这种硬数字**——比放一段好听的音频有说服力得多。单人也能完整体验：一个人录 8 句，系统当 8 个人拼。

**与已有产品的差异**：Smule Duet/Group 每人各唱完整段落、靠客户端时间戳对齐，不做跨人音准归一与自动择优；全民K歌的合唱与 [「一起唱」（2022-04 上线）](https://finance.sina.cn/tech/2022-04-15/detail-imcwiwst2028752.d.html) 是二人异步对唱模板，声部人工预分配；抖音合拍音频层各自独立；网易云“一起听”不涉及 UGC 录制；[Acapella by Mixcord](https://www.mixcord.co/pages/acapella-singing-app) 是一个人录多轨自我叠加。**留下的空白很清晰：N 人碎片 → 一首成品的全自动流水线，业内没有成品。**

**版权与内容安全（TME 落地的真实门槛）**：伴奏方面，K 歌场景授权不等于“生成一条新的完整录音制品并对外分发”，后者需要单独的改编权与录音制作授权——首发应限定在 TME 自有版权曲目或腾讯音乐人原创歌，绕开谈判周期。UGC 侧每条上传过 ASR 加文本审核，声纹层做未成年人保护与名人冒充识别。人格权侧，民法典第 1023 条规定声音参照肖像权保护，上传协议必须取得明示授权。**把这一节完整写进 PPT，是可行性评分的加分项**——它证明你懂这个功能真正会卡在哪里。

**致命风险**（1）“听起来像一首歌”这条线极窄，难在修音自然度；缓解是让万人垫音层承担主要听感；（2）**真实规模演示不了**，“万人”需要 TME 的首页资源位，2 人团队做不到；（3）版权不可自决。

**评分**：用户价值 8 ｜ 可行性 7 ｜ 创新性 8 ｜ TME 可落地 7

## I. 赛道一 · QQ音乐/酷狗：听感补偿，为“听不完整”的人重建音乐

**先给人群判断**：听障不是一个群体，必须切开。全聋人群走振动路线——目标窄、Apple 已做、且验证需要真实聋人被试。20 天内既做不深也证不了。**真正的产品机会在轻中度/高频听损人群**：他们**本来就在用 QQ音乐和酷狗听歌，只是听得不完整**。高频衰减让齿音、镲片、弦乐泛音、女声高音成片消失，音乐变得“闷”——但他们往往不认为自己有听力问题，只以为“这首歌录得不好”。

**一句话定义**：每个人的耳朵不一样，所以每个人该听到的音乐不一样。

**问题洞察**：一位 63 岁用户用酷狗听歌，4kHz 以上听阈已经掉了 40dB。他听到的是一个低频厚、高频空的版本，人声齿音消失导致歌词可懂度下降。他以为是手机音质差，于是把音量开到最大——而这只放大了他本来就听得见的低频，反而更糟，还加速损伤。**他不需要助听器，他需要播放器知道他的听力曲线长什么样。**

**目标用户**：WHO 口径下[中国听障人士约 2780 万，而第二次全国残疾人抽样调查显示仅 7.31% 实际使用辅助器具](https://m.thepaper.cn/newsDetail_forward_27339862)。[《中国听力健康报告（2025）》：60 岁及以上听力损失人数超 2000 万，65 岁以上约 1/3 存在听力残疾，80 岁以上约 90% 有不同程度听损](https://www.chinanews.com/life/2025/12-17/10535317.shtml)。加上年轻的噪声性听损人群。**可触达千万到亿级，且高度集中在酷狗/酷我的中老年盘里。**

**核心场景**：设置里看到“听感个性化”。戴上耳机，3 分钟完成一次纯音自测：不同频率的纯音由弱渐强，听到就点一下。测完出一张“听感倾斜曲线”，页面告诉他：“你在 4kHz 以上的听感比 1kHz 低约 35dB——这首歌里大约 28% 的高频信息你没有听到。”下面是一个可视化：歌曲频谱被切成两半，上半部分灰掉，标注“这是你正在错过的部分”。然后是一键 A/B。他切了三次，第三次摘下耳机说“这个镲片我十年没听见了”。

**功能清单**

| 功能 | 说明 | MVP |
| --- | --- | --- |
| 3 分钟纯音自测 | Web Audio，7 频点双耳分离 | 是 |
| 听感倾斜曲线 | 以 1kHz 自参考的相对曲线 | 是 |
| 个性化增益生成 | 半增益法则 + 音乐向修正 | 是 |
| 实时补偿播放 | 8 频段 WDRC + 输出限幅 | 是 |
| A/B 一键对比 | 原始/补偿即时切换 | 是 |
| “你错过的部分”可视化 | 按个人听阈切分频谱 | 是 |
| 跨端档案同步 | 手机/PC/车机一致 | 11.2 |
| 节拍触觉增强 | 低频包络驱动马达 | P1 |

**技术路径**

1. **测听**：Web Audio 生成 0.25/0.5/1/2/4/6/8 kHz 纯音，左右耳独立，改良 Hughson-Westlake 升降法（5dB 降 / 10dB 升）。**校准是这条路最硬的问题**：浏览器不知道绝对声压级，所以严禁声称输出临床听力图。三层解法：以 1kHz 为自参考锚点，只输出**相对倾斜曲线**（对补偿来说已够用，因为补偿本质上补的是频率间的不平衡）；内置常见耳机型号的 RETSPL 粗校准表；开测前用一段标准语音做主观锚定。
2. **增益处方**：以半增益法则（增益 ≈ 听阈损失的一半）为 baseline。**注意 NAL-NL2 是为语音可懂度优化的处方，不能直接搬到音乐上**——语音处方用 3:1 以上压缩比并削减低频，那会把音乐的动态和厚度毁掉。采用“NAL-NL2 骨架 + 音乐修正”：压缩比降到 1.5–2:1，带宽保留到 10–12kHz，不做语音式低频削减。
3. **实时链路**：AudioWorklet 里做 Linkwitz-Riley 8 频段分频 → 每段独立 WDRC（5ms 快启动 / 100–500ms 慢释放）→ 总输出限幅。**限幅不是可选项**：听损者普遍有响度重振（recruitment），动态范围被压窄，一个 30dB 的高频增益可能直接造成痛感。

**能不能做成可跑 Demo**：能，全部是 Web Audio，纯前端静态页，零后端。真正的问题是**可信度**。两个办法把它拉回来：

- **临床比对**：找 3–5 位有医院听力图报告的用户，把 Web 自测结果与临床纯音听阈做相关性比对，报出各频点平均绝对误差。哪怕 n=5，这也是“你验证过真实用户吗”这个必问题的**唯一正确答案**。
- **模拟听损现场演示**：用分频衰减滤波器在正常听力的评委耳朵上模拟出高频听损，让他亲耳听“模拟听损 → 补偿后”的切换。**这是路演上冲击力最强的 30 秒**，零伦理风险、完全可控。

**关于振动/可视化路线（降为 P1）**：手机的 X 轴线性马达（LRA）谐振频率通常在 150–235Hz，Q 值高、有效带宽窄（约 100–300Hz）。**物理上它只能传达节拍强弱，传达不了旋律和音色**——这是器件天花板，不是算法问题。而且 Web 端 `navigator.vibrate()` 只有时长没有强度。可视化要避免沦为“老式频谱仪”，唯一的办法是**让它由个人听力图驱动**：不画频谱，画“你听不到的那部分”。这既是科普、又是转化钩子、又是别人没做过的视觉，因为它必须有个性化听力数据才成立。

**空白非常清楚：跨平台的、在内容 App 内的、为「音乐」而非「语音」调校的听感补偿。** 现有方案要么系统级（绑手机品牌）、要么硬件级（绑耳机品牌）、要么语音处方。而 QQ音乐/酷狗横跨 iOS/Android/PC/Web/车机——**跨端一致的听感档案，恰恰是 TME 能做而 Apple 和华为结构上做不了的事。**

**（9月24日更新）撞车了：QQ音乐已经有。** 银河音效的“个性定制”已经是[耳廓扫描 + 听九段不同频率的声音测听感 → 生成专属音效模式](https://www.uisdc.com/hunter/0221380931.html)，在“我的 → 设置”里，会员功能。所以**不是缺产品位置，位置已经被占了**。

剩下的差异只有四点，这是唯一的立足点：**处方目标不同**（它调的是悦耳，你调的是听得全，两个目标在频响上经常是反的）；**人群不同**（九段测试找的是偏好，不是听阈损失）；**它是会员功能**，最需要它的听损老人被挡在付费墙后面；它不告诉你“你正在错过什么”。

这把 I 的创新性从 7 打到 5，与 D 是同一种病：**撞在 TME 自己已有的能力上**。反过来可行性涨了——基建已有，你是换处方不是从零建。讲法决定生死：说“你们没做这个”就输；说“你们做了，但把最需要的人挡在付费墙外，而且调的是悦耳不是完整”就赢。

**为什么 QQ音乐现在没做**：一是历史上被归类为“系统音效”而非“内容功能”，音乐 App 只敢做 EQ 预设（摇滚/流行/人声），从没敢做个性化听力测量；二是**合规恐惧**——助听器在中国是二类医疗器械，任何带诊断意味的宣称都是红线；三是中老年用户不是 QQ音乐主盘（在酷狗/酷我盘里更大），组织上无人认领。

**致命风险**

1. **合规红线**。全程必须用“听感个性化 / 音质补偿”措辞，**绝不能出现“听力测试”“助听”“诊断”**，界面固定位置放免责声明并引导就医。主动写进 PRD 反而让评委觉得你专业。
2. **“苹果已经做过了”**。反击三点：中国大陆不可用（官方页面为证）、绑定单一耳机、且是语音处方。
3. **“你验证过真实用户吗”**。这题没有话术能绕过去，只能真的去做。**它的周期比写代码长，今天就该开始约。**

## 9 月 24 日修正：结论从 I 改为 E

**改主意的原因只有一个：QQ音乐银河音效已经有耳廓扫描加九段听感测试的个性定制。** 我上次推 I 的第一理由是“唯一没有短板”，现在它有短板了，而且是最难辩护的那种——评委自己的团队做过。

**不再按总分选，因为总分已经没有区分度了。** 前四名挤在 38–41 分，这就是你们选不出来的数学原因。换一个判据：

**可修复的风险，赢过不可修复的风险。**

- E 的风险是可演示性——**这是工程问题**：提前录 8–10 人的真实反应视频，再加一张 20–30 人的 (α, β) 收敛散点图。点明显分散，就证明了个体差异真实存在、必须个性化——不需要任何人亲身体验就看得懂。
- I 和 D 的风险是撞车——**这不是工程问题**。你没办法让评委忘记自己团队做过什么。

**E 是赛道一里唯一没撞车的。** 银河音效解决的是“听别人的音乐更好听”，自听还原解决的是“听我自己的声音像我”——两个不同的问题，而且搜不到主流产品做过。它的创新性 9 是真实的。

另外三条：工程风险全场最低（纯 Web Audio、几百行、零后端零模型），在只剩十几天时权重极高；痛点直接在全民K歌的核心漏斗上（录完不发）；以及它是九个里最吃“调 EQ 的耳朵”的一个——那条曲线调得自然不自然，是内行与外行的分水岭。

**一句话叙事**：所有人都在做让你更好听，没有人做让你更像你自己。

**兜底**：若 spike 后发现自听还原的效果连你们自己都听不出来，切 **C**，不要切 I 或 D（那两个撞车）。

## 最终推荐：做 I，但换一个叙事

**主选：I 听感补偿。备选：D 音域变调（工程风险最低的兜底）。赛道二如果一定要投，投 C。**

### 先说一个关键的叙事改动

不要把它做成无障碍功能。一旦贴上“听障公益”标签，评委的第一反应是“感人，但多少人用”，你就被按在 TAM 问题上了。

**正确的定位是：每个人的耳朵都不一样，所以每个人该听到的音乐不一样。**

这个框架下，听损人群是效果最剧烈的那一端，但不是唯一一端：长期大音量戴耳机的年轻人已经有隐性高频损伤，而他们一无所知。“测一下你正在错过音乐的百分之几”是一个**全民都想点的钩子**，也是天然的社交传播卡片。无障碍是它的内核与价值观底座，不是它的封面。这样一来，TAM 从“听障人群”扩到“所有戴耳机听歌的人”，而且这个扩大是诚实的。

### 为什么是它

**一、它是唯一一个在五个维度上都没有短板的方案。** 其他每个都有一个致命的 5 分以下项：A 和 B 是可落地性，E 是可演示性，D 是创新性。一个十二强里的评审，每个评委只看几分钟，**短板比长板致命**。

**二、它有一条对手无法反驳的事实护城河。** Apple 的 Hearing Test 与 Hearing Aid 功能在中国大陆不可用（官方功能可用性页面为证），Mimi 是 B2B SDK，三星/华为绑设备。**跨端一致的听感档案是 TME 能做、Apple 和华为结构上做不了的事。** 这句话是你路演 PPT 的第二页。

**三、落地成本低到不像话。** 一个 AudioWorklet 插在播放链路里。不改版权链路、不改结算、不需新硬件、不需 BD 谈合作。而酷狗/酷我的中老年盘是现成的场景。这直接命中“TME 下个版本能不能排”。

**四、它给 TME 的不只是功能，是一个品牌资产。** 一等奖作品要能对外讲故事。“腾讯音乐让 2000 万听损老人重新听见完整的音乐”是一句能上年度报告的话。这是其他八个方案都给不了的东西。

**五、它的能力需求刚好落在你们的舒适区。** 纯 Web Audio：纯音发生、升降法流程控制、分频滤波器组、多段 WDRC。不需训模型、不需 GPU 在线服务、不需冷启动运营、不需版权谈判。**20 天两个人，这是唯一一类能真的做完并且做得精致的东西。** 而你的混音耳朵在这里是真优势——调一条听起来自然的多段补偿曲线，和调一个母带链是同一种手感。

**六、它有一个 30 秒就能击中全场的现场演示。** 请一位评委戴上耳机，先用滤波器给他模拟出高频听损，让他听一段熟悉的歌，再切到补偿后。**他会当场经历一遍你的用户旅程。** 这个演示零伦理风险、完全可控、不依赖网络。对比一下 E：同样是 EQ，但 E 的效果评委根本感受不到。

### 诚实的减分项

**创新性只有 7，这是它最弱的一项。** 听力补偿本身是成熟技术，助听器行业做了几十年。你的创新不在算法，在**产品位置**（把它从系统设置/医疗器械里搬到内容 App 里）和**调校目标**（为音乐而非语音）。这两点必须在 PPT 里说透，否则评委会当成“做了个 EQ”。具体抵消手段：把 **NAL-NL2 不能直接搬到音乐上**这一节写成一页（压缩比从 3:1 降到 1.5–2:1、带宽保留到 12kHz、不做语音式低频削减）——**这是一个只有懂音乐的人才会想到的区分，它就是你的创新性证据。**

**第二个减分项是真实用户验证。** 评委一定会问。这件事**周期比写代码长，今天就要开始约**：找 3–5 位有医院纯音听力图报告的人（长辈、学校听力学/耳鼻喉科资源都行），把你的 Web 自测结果与临床值做相关性比对，报各频点平均绝对误差。n=5 也足够把这个问题从“你没验证过”变成“你验证过，只是样本少”。

### 两个可以直接拿走的强化

**把 E 的 A/B 二分交互搬过来。** 纯音测听完之后加一个可选的 4 轮“哪个更好听”微调，把客观听阈曲线往主观偏好上拉一点。这又能规避“测不准”的口碑，又能让你在 PPT 里多一个交互创新点。

**把酷狗而不是 QQ音乐写成主落地产品。** 中老年听损人群在酷狗/酷我的盘里大得多。你主动选对了产品，评委会觉得你真的看过 TME 的业务盘，而不是随手挑了个最有名的 App。
